# OASX Android 客户端开发规范与实施提示词

## 一、项目定位

你是一名资深 Android 工程师、移动端 UI/UX 设计师，同时具备 Kotlin、Jetpack Compose、Material Design 3 和客户端架构设计经验。

现在需要为 OAS（Onmyoji Auto Script）开发一个 Android 客户端，项目名称为 OASX Android。

OASX Android 是 OAS 自动化脚本系统的移动端管理客户端。它的主要职责是让用户通过 Android 设备查看游戏账号信息、管理任务、监控执行状态以及查看运行记录。

它不是一个简单的 WPF 界面移植项目，也不是将桌面端的布局压缩到手机屏幕上。

必须针对移动设备重新设计信息架构、页面布局、交互方式和导航结构。

核心目标：

1. 功能清晰，操作直观。
2. 界面简洁、克制，符合 Android 原生设计习惯。
3. 充分利用 Material Design 3。
4. 兼容不同尺寸和比例的 Android 设备。
5. 与现有 OAS 后端保持正确的数据通信。
6. 与 OASX 桌面端保持一致的业务逻辑和设计语言。
7. 正确处理多账号、多任务和多调度器环境。

## 二、开发前必须进行的项目分析

不要立即开始编写界面。

首先检查现有项目及 OAS 后端，确认以下内容：

### 1. 后端接口分析

检查 OAS 当前提供的 API、通信协议和数据结构。

重点确认：

- 服务地址及连接方式
- API 身份验证机制
- 账号管理接口
- 账号资源查询接口
- 任务列表及任务配置接口
- 任务启用、禁用及控制接口
- 调度器状态接口
- 当前任务执行状态接口
- 执行历史与日志接口
- 异常信息及错误响应结构

建立接口清单，记录每个接口的请求参数、返回数据、错误情况及使用场景。

严禁虚构 API、请求参数、返回字段或后端功能。

如果某项功能缺少接口支持，应明确标记为暂不可实现，而不是使用模拟数据伪装成真实功能。

### 2. 业务模型分析

重点理解以下实体之间的关系：

- Account：游戏账号
- Scheduler：任务调度器
- Task：任务
- Execution：任务执行记录
- Resource：游戏资源

必须特别检查账号和调度器之间的实际关联关系，不要假设它们是一对一关系。

### 3. 现有桌面端分析

如果可以访问 OASX WPF 项目，应分析：

- 现有功能模块
- API 调用方式
- 数据模型
- 业务规则
- 账号管理逻辑
- 任务管理逻辑
- 现有交互流程

复用已经验证的业务逻辑和数据定义，但不要直接复制 WPF 的布局和控件设计。

## 三、技术架构

如果没有现成的 Android 技术栈约束，优先使用：

- Kotlin
- Jetpack Compose
- Material Design 3
- MVVM
- Repository Pattern
- Kotlin Coroutines
- Kotlin Flow
- Retrofit + OkHttp
- Kotlin Serialization 或项目已有的 JSON 序列化方案
- DataStore
- Room（确实需要结构化本地数据时）

建议采用分层结构：

### Presentation Layer

负责：

- Compose 页面
- UI 状态
- ViewModel
- 用户交互
- 页面导航

### Domain Layer

负责：

- 业务模型
- 业务规则
- UseCase
- 业务数据转换

### Data Layer

负责：

- API 请求
- Repository 实现
- DTO
- 本地数据存储
- 数据映射
- 错误处理

要求：

- UI 不应直接发起网络请求。
- ViewModel 不应承担所有业务逻辑。
- API DTO 与 UI Model 应适当分离。
- 使用 StateFlow 管理 UI 状态。
- 正确处理协程取消和页面生命周期。
- 不要为了架构形式而过度抽象。

## 四、核心信息架构

Android 版本应围绕游戏账号组织主要业务信息。

建议采用底部导航栏，控制主要导航入口数量。

初步建议：

1. 首页
2. 资产
3. 任务
4. 记录
5. 设置

如果实际功能规模不适合五个底部入口，可以根据 Android 的导航规范重新调整。

### 4.1 首页 Dashboard

首页是整个应用的主要入口。

用户打开应用后，应当快速知道：

- 当前查看的是哪个游戏账号。
- OAS 服务是否正常。
- 当前账号是否有正在执行的任务。
- 是否存在任务异常。
- 最近任务执行情况。

建议页面结构：

**顶部区域**
- 当前账号头像或标识
- 账号名称
- 区服
- 账号切换入口
- 必要的连接状态

**当前任务区域**
- 正在执行的任务
- 任务状态
- 开始时间
- 执行阶段或次数（仅当后端提供真实数据时）
- 支持的任务控制操作

**任务概况**
- 已完成任务
- 待执行任务
- 失败任务

**运行状态**
- OAS 服务状态
- 调度器状态
- 连接状态
- 异常提醒

**最近执行记录**
- 任务名称
- 执行结果
- 执行时间
- 耗时
- 日志入口

不要把桌面端的大量卡片原样堆叠到手机上。

优先使用纵向信息流、清晰的分组和适量的摘要信息。

### 4.2 资产页面

资产页面以当前游戏账号为核心。

展示当前账号的：

- 金币
- 勾玉
- 体力
- 荣誉
- 勋章
- 神秘符咒
- 现世符咒
- 其他 OAS 实际支持的资源

具体资源种类以真实 API 数据为准。

设计要求：

- 使用清晰的资源分组。
- 数值应具有足够的视觉权重。
- 资源名称和数值保持明确对应关系。
- 合理利用网格布局。
- 避免过多装饰性图标。
- 避免每个资源都使用过度复杂的卡片。
- 支持资源数据加载、无数据和错误状态。

资产页面不应显示调度器选择器。

### 4.3 任务页面

展示当前账号关联的任务。

建议支持：

- 任务列表
- 任务分类
- 任务启用状态
- 当前执行状态
- 任务详情
- 任务配置
- 后端实际支持的任务控制操作

任务数量较多时，应使用分类、搜索或折叠分组控制信息密度。

不要将调度器作为默认的首要分类维度。

### 4.4 执行记录页面

展示真实的历史执行记录。

建议字段：

- 任务名称
- 所属账号
- 执行结果
- 开始时间
- 耗时
- 错误摘要

支持按账号、时间及执行结果筛选。

调度器信息可以作为详情字段或排障筛选条件，不应默认占据主要视觉位置。

### 4.5 设置页面

根据实际功能提供：

- OAS 服务地址
- 连接配置
- 身份验证
- 主题设置
- 通知设置
- 应用信息
- 数据刷新设置
- 其他实际存在的客户端配置

敏感凭据必须安全存储，不得明文写入日志或普通配置文件。

## 五、核心设计原则：账号与调度器分离

这是整个项目必须遵循的全局业务规则。

**游戏账号是业务主体，调度器是任务执行与调度机制。**

两者不属于同一层级。

### Account

账号决定业务数据归属。

包括：

- 游戏资源
- 游戏账号信息
- 账号统计
- 账号关联的任务
- 账号关联的执行记录

### Scheduler

调度器负责：

- 任务调度
- 任务执行管理
- 调度器运行状态
- 运行异常
- 执行环境信息

### UI 设计约束

1. 多账号模式下，账号是主要操作上下文。
2. 建立全局当前账号上下文。
3. 账号选择器不应在每个页面重复出现。
4. 资产页面不应出现无意义的调度器选择器。
5. 切换调度器不应改变账号资产数据。
6. 切换账号不应错误地改变全局调度器状态。
7. Dashboard 优先呈现当前账号和账号任务。
8. 调度器状态作为系统运行信息展示。
9. 任务和执行记录应明确账号归属。
10. 全局任务或无法确定归属的任务必须单独标记。

如果真实后端的数据关系与上述设计假设不同，应先分析实际数据模型，再调整实现。不得为了 UI 方便而改变业务语义。

## 六、Android UI/UX 设计规范

### 6.1 整体视觉风格

采用 Material Design 3，但不要将默认 Material 组件不加设计地直接堆叠。

整体视觉方向：

- 简洁
- 克制
- 清晰
- 轻量
- 有明确的信息层级
- 接近现代 Android 原生应用

与 OASX WPF 桌面端保持品牌和设计语言的一致性，但不要求像素级一致。

### 6.2 主题

必须支持：

- Light Theme
- Dark Theme
- System Default

通过统一的 ColorScheme 和 Theme 管理颜色。

不要在页面中直接硬编码颜色。

### 6.3 排版

使用 Android 系统字体及 Material 3 Typography。

合理区分：

- 页面标题
- 模块标题
- 主要数值
- 正文
- 辅助说明
- 状态文字

资源数值和任务状态应容易识别，但不要使用过多粗体和超大字号。

### 6.4 布局

以手机竖屏为主要设计场景，同时兼容：

- 小屏手机
- 大屏手机
- 平板
- 横屏

使用 WindowSizeClass 或适当的自适应布局方案。

避免固定宽高导致内容被裁切。

### 6.5 交互

优先采用 Android 用户熟悉的交互方式：

- Bottom Navigation
- Top App Bar
- Modal Bottom Sheet
- Dropdown Menu
- Snackbar
- Dialog
- Pull-to-Refresh（适用于确实需要手动刷新的页面）
- Swipe Gesture（仅在操作语义明确时使用）

危险操作必须提供确认。

高频操作应减少不必要的点击步骤。

### 6.6 无障碍

必须考虑：

- 触控区域尺寸
- 文本缩放
- 内容描述
- 色彩对比度
- 状态不能只通过颜色表达
- TalkBack 基础支持

## 七、网络与运行状态

移动端需要考虑网络环境不稳定的情况。

至少处理：

- 服务地址不可达
- 请求超时
- 身份验证失败
- 网络断开
- API 返回异常
- 数据为空
- 数据加载中
- 数据刷新失败

要求：

1. 明确区分客户端网络状态和 OAS 服务状态。
2. 不要将网络连接正常误判为 OAS 服务正常。
3. 不要在请求失败时继续展示看似实时的旧数据而不做标记。
4. 如果展示缓存数据，应标明数据更新时间。
5. 避免无节制的自动刷新。
6. 对高频状态查询采用合理的刷新策略。

---

## 八、后台运行与通知

先确认 Android 客户端是否确实需要后台运行能力。

如果需要：

- 评估 WorkManager 是否适用。
- 对需要持续连接的场景，评估 Android 后台执行限制。
- 根据 Android 版本处理通知权限。
- 仅在有实际价值时发送任务异常或执行结果通知。
- 避免频繁、重复或无意义的通知。

特别注意：

Android 客户端负责管理和监控 OAS，不应擅自把 OAS 的任务执行逻辑移植到手机后台。

除非产品需求和后端架构明确要求，否则不要让手机承担游戏脚本的实际执行工作。

---

## 九、安全要求

- 使用安全方式保存认证信息。
- 不在日志中输出 Token、密码或敏感配置。
- 不允许通过不安全的方式绕过 HTTPS 证书校验。
- 对服务地址和网络请求进行必要的校验。
- 不要将密钥硬编码进客户端。
- 断开账号或服务连接时，正确处理本地敏感数据。

## 十、开发流程

按照以下阶段实施，不要一次性生成整个应用。

### Phase 1：项目分析

- 分析 OAS 后端 API。
- 分析现有 OASX 桌面端。
- 确认账号、调度器和任务的数据关系。
- 输出 API 清单和业务模型。
- 提出 Android 技术架构。

### Phase 2：设计系统

- 确定导航结构。
- 建立 Material 3 主题。
- 建立 Typography。
- 建立颜色、间距、圆角等设计 Token。
- 建立通用组件。
- 设计主要页面的低保真布局。

### Phase 3：基础框架

- 建立网络层。
- 建立 Repository。
- 建立 ViewModel。
- 建立导航系统。
- 建立全局账号上下文。
- 建立统一错误处理。

### Phase 4：核心功能

建议按以下顺序实现：

1. 服务连接和配置
2. 账号管理与账号切换
3. Dashboard
4. 资产页面
5. 任务管理
6. 执行记录
7. 日志与设置

### Phase 5：测试与优化

- 测试不同 Android 屏幕尺寸。
- 测试浅色与深色主题。
- 测试账号切换。
- 测试多账号数据隔离。
- 测试多调度器场景。
- 测试网络异常。
- 测试应用前后台切换。
- 测试旋转屏幕及页面状态恢复。
- 检查性能和内存使用。

- 遵循 Kotlin 官方编码规范。
- 使用清晰的命名。
- 保持模块职责单一。
- 避免过度复杂的 Compose 页面。
- 提取合理的可复用组件。
- 不要为了复用而抽象简单的一次性 UI。
- 关键业务逻辑应具备测试。
- 不允许用大量假数据掩盖接口尚未实现的问题。
- 不要随意修改已有后端协议。
- 每个开发阶段结束后都应保证项目能够正常编译。

## 最终目标

OASX Android 应当成为一个真正适合移动设备使用的 OAS 管理客户端。

它应当让用户能够方便地管理游戏账号、查看资源、管理任务、监控运行状态和检查执行记录。

始终遵循以下原则：

**账号决定业务数据归属，任务描述工作内容，调度器负责执行，客户端负责管理和呈现。**

不要让后端内部的技术结构决定移动端的用户体验。

不要为了追求功能数量牺牲信息层级、交互效率和界面质量。
